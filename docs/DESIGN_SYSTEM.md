## Decorative imagery and accessible content

- Use CSS backgrounds or decorative image elements for hero/footer imagery. An image element should have empty alt text when decorative; do not add redundant screen-reader announcements.
- Keep headings, navigation labels, actions, and meaningful text in accessible HTML. Never embed important content only in an image.
- Use an overlay or solid text region where needed; verify sufficient contrast for the text's size/weight against the actual image crop in both themes. A dark image alone does not establish contrast compliance.
- Prefer `alt=""` for generic property imagery when the surrounding card already provides real listing details. The whole card must remain meaningful without the image.
- Do not claim the illustrations depict actual listings, derive property facts from them, or invent amenities, views, styles, or locations.
- Plan a visible or accessible clarification such as “Property imagery is illustrative” near the result cards.

## Responsive sizing and cropping

Hero/footer images start at approximately 16:9; property images start at 4:3. Preserve these ratios where practical. Use fluid widths, reserved aspect ratios, and `object-fit: cover` or `background-size: cover` when filling a container. Use image width/height attributes or CSS aspect ratio to reserve space before decoding. Avoid fixed widths that cause horizontal overflow.

Start centered and use the per-image focal recommendations in the inventory when another ratio requires cropping. Hero/footer architecture is concentrated toward the right; the california-hills illustration is more concentrated left/center. Do not cut off the important architectural subject merely to retain sky or foreground. Different desktop/mobile crop rules may be appropriate, but must be reviewed in the rendered layout. The implemented hero uses centered desktop positioning and 75% 50% on mobile; both themes were inspected at all requested widths in Chrome emulation. Property cards use the Phase 6.2B crops; footer imagery is integrated in Phase 6.3A below.

## Theme implementation

`frontend/public/theme-init.js` runs synchronously in the HTML head, before React and styles paint. It reads `haven-theme` from localStorage; absent/invalid values follow `prefers-color-scheme`. It sets the root `data-theme` so the first painted palette matches the saved/system preference. Storage failures fall back to System rather than blocking rendering.

`useTheme` keeps the preference (System/Light/Dark) separate from the resolved Light/Dark palette. It subscribes to system changes, respects an explicit override, writes user choices to localStorage, updates the root attribute, and removes its listener on cleanup. Choosing System restores live system tracking. If storage is unavailable the override still works for the current mount. Cross-tab preference synchronization is not implemented.

`SiteHeader` uses a native button with role=switch, a stable Dark appearance label, aria-checked, and a description naming the next action. Auto restores the existing system preference and exposes aria-pressed. The Phase 6.3A extension below describes animation and loading behavior.

Text and its backing surfaces change together to preserve contrast. Exposed page background, toggle track/border, thumb/icons, and decorative hero/footer imagery animate as described in the Phase 6.3A extension below. Reduced motion disables these transitions.

Do not merely rename an extension; conversion must produce the actual format. Report any future lossy transformations and compare quality. The organization pass made no transformations. Phase 6.1B adds reported lossy hero derivatives using Pillow in an ignored frontend-local tooling environment; no image-processing runtime dependency is shipped.

Prioritize the visible main hero image. Plan lazy loading for below-the-fold listing/footer images, reserve layout space, and render only the current page's card images. The hero now advertises verified 640/1024/1672px WebP sources with high fetch priority and eager loading. Footer/property originals remain archival inputs; responsive WebP derivatives serve the implemented UI. A successful build only proves packaging, not loading strategy, crop quality, or contrast.
